> **문서 목적**: 본 문서는 **날씨 및 대중교통 연계 추천 웹 서비스(Weather & Transit Web)** 프로젝트를 개발하며 직면했던 주요 기술적 난관과 이를 해결하기 위해 내린 아키텍처·알고리즘적 의사결정을 **STAR (Situation - Task - Action - Result)** 기법으로 정리한 발표·면접 전용 트러블슈팅 자료입니다.
> 
> *최종 갱신일: 2026-11-03*

## 📌 발표 스토리텔링 구조 가이드
캡스톤 디자인 평가 및 기술 면접에서는 **"단순히 기능을 만들었다"** 는 나열식 설명보다, **"어떤 현실적 한계를 발견했고, 어떤 기술적 고민을 통해 극복했는가"** 를 증명할 때 가장 높은 평가를 받습니다.

```
[1. 직면한 문제 (Situation & Task)]
   ➔ 외부 API 불안정, 모델 차원 불일치, 안전 위험, 모바일 UX 왜곡 등
[2. 해결 과정 및 기술적 결정 (Action & Trade-off)]
   ➔ 단순 우회가 아닌 구조적 원인 분석 및 아키텍처/알고리즘 개선
[3. 정량적/정성적 성과 (Result & Verification)]
   ➔ 응답 속도 단축, 무장애 서빙, 안전 경로 보장, 시연 완성도 확보
[4. 발표 어필 포인트 (Takeaway)]
   ➔ 발표 슬라이드 한 줄 요약 및 심사위원 질의 대응
```

### ① [이슈 #98] 지도를 노원구로 옮겼는데 날씨는 계속 강남구? (지도-기상 공간 불일치 해결)
* **내가 발견한 문제 (이슈 발의 배경)**:
  * *"지도를 마우스로 드래그해서 노원구나 강서구, 판교 등으로 이동했는데도, 우측 날씨 카드에는 여전히 처음 선택된 '강남구 18도'로 고정되어 나오는 공간 정보 불일치를 발견했습니다."*
* **해결 방법 (개념 설명)**:
  * *"사용자가 지도를 움직여서 멈추면(`moveend`), 지도의 중심 위경도 좌표를 감지해서 해당 자치구의 실시간 날씨를 자동으로 다시 조회하도록 연동했습니다. 마우스를 조금만 움직여도 API가 과도하게 호출되는 것을 막기 위해 `0.5초` 디바운스(지연) 및 캐싱 가드도 함께 적용했습니다."*
* **내가 직접 테스트한 결과**:
  * 지도를 다른 동네로 옮기면 상단 배지가 `[지도 중심 기준 - 종로구]`와 같이 자동으로 바뀌면서 실제 그 지역의 날씨가 즉각 반영되는 것을 브라우저에서 직접 검증함.

## 1. [AI & 서빙] 32차원 ONNX 추론 모델 피처 드리프트 및 입력 차원 불일치

### ① 상황 및 문제 (Situation & Task)
* 기상(기온, 강수, 풍속, 습도 등), 교통(혼잡도, 지연율), 시간대 특성을 통합하여 혼잡도를 예측하는 경량 ONNX 모델을 서빙하는 과정에서, **런타임 시 모델 입력 텐서 차원(32차원)과 백엔드 전처리 벡터 수가 불일치하여 추론 서버 런타임 오류(Shape Mismatch)** 가 간헐적으로 발생하는 위험이 있었습니다.
* 개발 단계에서 피처 순서가 뒤바뀌거나 누락될 경우 모델이 엉뚱한 예측값을 내놓는 **피처 드리프트(Feature Drift)** 문제를 사전에 감지할 수단이 부재했습니다.

### ② 해결 조치 (Action)
* **단일 진실 공급원(SSOT) 구축**: 모델이 요구하는 32개 피처의 이름, 타입, 기본값, 순서를 정의한 `models/feature_schema.json`을 단일 표준으로 확립.
* **서버 부팅 시 자가 치유 검증 파이프라인 탑재**: 백엔드 기동(`main.py`) 시 ONNX 런타임의 입력 메타데이터와 `feature_schema.json`의 32차원 일치 여부를 전수 자동 검증.
* **헬스체크 엔드포인트 연동**: `GET /health` 호출 시 모델 차원이 정확히 `32`인지, `feature_schema.status`가 `verified`인지 실시간 모니터링할 수 있도록 보장.

### ③ 결과 및 발표 어필 포인트 (Result & Takeaway)
* **결과**: 모델 서빙 시 입력 데이터 불일치로 인한 런타임 크래시 발생률 `0%` 달성.
* **발표 멘트**:
  > *"인공지능 모델을 실제 웹 서비스에 올릴 때 가장 흔히 겪는 문제가 데이터 파이프라인의 피처 순서 불일치입니다. 저희는 `feature_schema.json`을 단일 진실 공급원(SSOT)으로 삼고, 서버 구동 시 모델과 스키마를 자동 검증하는 자가 치유 체계를 구축하여 운영 안정성을 확보했습니다."*

## 2. [실시간 공공 데이터] 서울시 버스 OpenAPI의 간헐적 지연 및 트래픽 쿼터 제한

### ① 상황 및 문제 (Situation & Task)
* 공공데이터포털(data.go.kr)의 서울시 버스 5종 OpenAPI(정류소, 노선, 버스위치, 버스도착, 환승)는 **응답 지연(수 초 소요)** 이 빈번하고, 서버 상태에 따라 간헐적으로 `500 Internal Server Error`나 타임아웃을 반환했습니다.
* 사용자가 경로를 검색하거나 정류소를 클릭할 때마다 매번 외부 API를 직접 호출하면 사용자 체감 대기시간이 극도로 길어지고 일일 허용 호출량(Quota)을 초과할 위험이 있었습니다.

### ② 해결 조치 (Action)
* **2단계 계층형 스마트 캐시(Memory + SQLite WAL) 설계**: `timeseries_cache.py`를 구현하여 초단위 메모리 캐시와 영속적 SQLite 캐시를 결합. 동시성 쓰기 성능을 위해 `WAL(Write-Ahead Logging)` 모드를 활성화.
* **우아한 성능 저하(Graceful Degradation) 및 서킷 브레이커 적용**: 외부 공공 API가 일시적으로 타임아웃되거나 에러를 뿜을 때 서비스를 중단하지 않고, 직전에 캐싱된 유효 데이터를 안전 폴백(Fallback)으로 반환하여 끊김 없는 사용자 경험 제공.

### ③ 결과 및 발표 어필 포인트 (Result & Takeaway)
* **결과**: 정류소 및 도착 정보 재조회 시 응답 지연을 외부 API 평균 `1.5~2.5초`에서 캐시 히트 시 `5ms 이하`로 `99% 이상 단축`.
* **발표 멘트**:
  > *"공공데이터 API는 언제든 지연되거나 죽을 수 있다는 전제하에 아키텍처를 설계했습니다. SQLite WAL 기반의 스마트 캐시와 안전 폴백 메커니즘을 적용하여, 외부 공공 서버 장애 상황에서도 사용자에게 중단 없는 실시간 정보를 제공하도록 구현했습니다."*

## 3. [공간 수학 & 연산] 기상청 단기예보 격자(LCC 투영좌표계) 실시간 변환 병목

### ① 상황 및 문제 (Situation & Task)
* 일반 스마트폰 GPS나 지도 좌표는 위경도(WGS84)를 사용하는 반면, 기상청 단기예보 OpenAPI는 **기상청 자체 정규 격자 좌표(X, Y)** 를 요구합니다.
* 사용자가 길찾기를 수행할 때마다 위경도를 기상청 격자로 변환하는 복잡한 삼각함수 연산이 반복 수행되었고, 서울시 25개 자치구별로 중복된 API 요청이 발생하여 백엔드 CPU 리소스가 낭비되었습니다.

### ② 해결 조치 (Action)
* **Lambert Conformal Conic(람베르트 정각원추 투영법) 공식의 파이썬 최적화**: 표준 지구 타원체 상수를 기반으로 WGS84 위경도와 기상청 격자(X, Y) 간 상호 변환 알고리즘을 수학적으로 벡터화.
* **자치구 중심 좌표 사전 인덱싱 및 격자 캐시 분리**: 25개 자치구별 대표 격자를 사전에 해싱하여 캐시 키로 관리함으로써 중복 좌표 변환 및 기상청 API 중복 호출을 원천 차단.

### ③ 결과 및 발표 어필 포인트 (Result & Takeaway)
* **결과**: 좌표 변환 오버헤드 `0ms` 수렴 및 동일 시간대 자치구 기상 API 호출 횟수를 획기적으로 절감.
* **발표 멘트**:
  > *"지도 표준 위경도와 기상청의 LCC 투영 격자 간 불일치 문제를 해결하기 위해, 지구 타원체 투영 공식을 최적화하고 자치구별 격자 해시 캐싱을 적용하여 실시간 경로 추천의 응답성을 극대화했습니다."*

## 4. [알고리즘 & 도메인 안전] 날씨 연계 기상 안전 게이트(Weather Gate)와 거리 왜곡 보정

### ① 상황 및 문제 (Situation & Task)
* **기존 길찾기 시스템의 한계**: 단순히 최단 시간(Shortest Time)만 계산하는 기존 알고리즘은 **폭우나 강풍이 부는 악천후에도 시간 단축만을 위해 따릉이(자전거)나 킥보드를 추천**하여 시민의 안전을 위협하는 치명적 맹점이 있었습니다.
* 또한 역과 정류소 간 거리를 단순 직선거리(Euclidean/Haversine)로만 계산하면 한강 교량이나 철도 단절, 실제 골목길 굴곡이 반영되지 않아 소요시간 왜곡이 발생했습니다.

### ② 해결 조치 (Action)
* **기상 안전 게이트(Weather Gate) 상태 머신 탑재**: 실시간 강수량(`rain > 0mm`)이나 강풍(`wind >= 10m/s`) 감지 시, 퍼스널 모빌리티(따릉이/도보 장거리)를 추천 경로에서 배제하고 지하철/버스 실내 환승 우선 경로로 자동 전환.
* **보행 및 자전거 실질 우회계수 보정**: 단순 직선거리에 서울시 보행 실측 우회계수(`1.22~1.28`)를 동적 적용하여 현실적인 도보·자전거 소요시간을 산출.

### ③ 결과 및 발표 어필 포인트 (Result & Takeaway)
* **결과**: 악천후 상황에서 퍼스널 모빌리티 위험 경로 추천 건수 `0건` 달성 (100% 안전 경로 보장).
* **발표 멘트**:
  > *"저희 프로젝트의 핵심 차별화 요소입니다. 일반 길찾기가 '가장 빠른 길'만 찾는다면, 저희는 '날씨를 이해하고 사람의 안전을 지키는 길'을 찾습니다. Weather Gate 알고리즘을 통해 비가 오는 순간 따릉이를 지하철 안전 경로로 자동 우회시킵니다."*

## 5. [프론트엔드/UX] 반응형 지도 뷰포트 가림 방지 및 모바일 UI 최적화

### ① 상황 및 문제 (Situation & Task)
* 데스크톱 PC 화면에 맞춰 제작된 대형 기상 카드와 경로 정보 패널이 **스마트폰 모바일 화면(폭 768px 이하)에서는 지도 전체를 덮어버려, 사용자가 정작 지도를 볼 수 없는 심각한 UX 결함**이 발생했습니다.
* 전역 CSS 미디어 쿼리로 인해 내부의 작은 2x2 기상 정보 그리드마저 강제로 1열로 무너져 화면 스크롤이 비정상적으로 길어지는 현상이 나타났습니다.

### ② 해결 조치 (Action)
* **PC와 모바일 아키텍처 이원화 (`App.tsx` vs `AppM.tsx`)**: 플랫폼별 특성을 온전히 반영할 수 있도록 진입점을 분리하고 기능은 100% 동기화 유지.
* **모바일 1줄 알약 배지 슬림화 및 범례 토글화**: 모바일 상단 경로/기상 정보를 콤팩트한 1줄 알약 형태로 축소하고, 불필요한 고정 버튼을 숨겨 지도 시야(Viewport)를 대폭 확보.
* **전용 클래스(`weather-metrics-grid`) 보호**: 내부 소형 2x2 메트릭 그리드가 외부 미디어 쿼리에 간섭받지 않도록 독립 격리 스타일 적용.

### ③ 결과 및 발표 어필 포인트 (Result & Takeaway)
* **결과**: 모바일 화면에서 지도 가림 면적을 기존 `70% 이상`에서 `15% 이하`로 축소, 한눈에 들어오는 지도 뷰포트 확보.
* **발표 멘트**:
  > *"모바일 사용자가 대중교통을 이용하면서 한 손으로도 쾌적하게 지도를 볼 수 있도록 모바일 전용 컴포넌트(`AppM.tsx`)를 분리 설계하고, 지도시야를 가리던 요소를 1줄 알약 배지로 슬림화하여 현장 사용성을 극대화했습니다."*

## 6. [인프라 & 확장성] Docker 리버스 프록시(Nginx)와 대규모 트래픽 대비 타일 설계 (#102)

### ① 상황 및 문제 (Situation & Task)
* **Docker 환경 경로 문제**: 로컬 개발 환경(`localhost:8000`)과 달리 컨테이너 배포 시 `VITE_API_BASE_URL=""` 환경에서 `new URL("/api/...")`가 오작동하여 네트워크 에러가 발생하는 환경 의존성 문제가 있었습니다.
* **외부 지도 타일 정책 한계**: OpenStreetMap 무료 타일 서버(`tile.openstreetmap.org`)를 브라우저에서 직접 호출할 경우, 대규모 트래픽 발생 시 사용 정책 위반으로 **사전 통보 없이 IP가 차단(403 Forbidden)** 될 수 있는 잠재 리스크를 식별했습니다.

### ② 해결 조치 (Action)
* **Nginx 리버스 프록시 단일 엔드포인트 확립**: 프론트엔드 Nginx가 `/api/` 요청을 백엔드 컨테이너(`backend:8000`)로 안전하게 라우팅하도록 구성하고, 프론트엔드는 템플릿 리터럴 상대 경로로 API 호출을 표준화.
* **대규모 트래픽 대비 아키텍처 설계 수립 (이슈 #102 선행 분석)**:
  * 1단계: Nginx 디스크 캐시 프록시(`location /tiles/`)를 통한 외부 요청 완충.
  * 2단계: PMTiles / Martin 기반 수도권 벡터 타일 자체 서빙 로드맵 및 ODbL 오픈소스 라이선스 고지 규격 수립.

### ③ 결과 및 발표 어필 포인트 (Result & Takeaway)
* **결과**: 단 한 번의 `docker compose up`으로 프론트/백엔드 완벽 구동 및 향후 서비스 확장을 위한 인프라 로드맵 확보.
* **발표 멘트**:
  > *"학생 과제 수준에 안주하지 않고, Docker 기반의 무중단 배포 구조와 함께 향후 서비스가 상용화되어 대규모 트래픽이 몰렸을 때 발생할 수 있는 지도 타일 차단 리스크와 오픈소스 라이선스(ODbL) 준수 방안까지 선제적으로 설계에 반영했습니다."*

### Q2. "공공데이터 OpenAPI가 느리거나 서버가 다운되면 서비스가 멈추지 않나요?"
* **모범 답변**:
  > *"공공데이터 API의 장애는 빈번히 일어납니다. 저희는 이를 방어하기 위해 **SQLite WAL 기반의 2단계 시계열 캐시(`timeseries_cache.py`)와 서킷 브레이커**를 자체 구축했습니다. 정상 시에는 외부 API 응답을 캐싱하여 5ms 이내로 초고속 응답을 제공하며, 외부 서버가 다운되더라도 캐시된 직전 데이터를 안전하게 폴백하여 서비스가 절대 중단되지 않도록 내결함성(Fault Tolerance)을 갖추었습니다."*

### Q3. "앞으로 실제 상용 서비스로 발전시킨다면 어떤 점을 보완해야 하나요?"
* **모범 답변**:
  > *"두 가지 인프라 확장을 준비해 두었습니다. 첫째는 **지도 타일의 자체 호스팅(이슈 #102)** 입니다. 현재 검토를 마친 PMTiles와 Nginx 캐시 프록시를 적용하여 외부 타일 서버 의존성과 IP 차단 위험을 원천 제거할 것입니다. 둘째는 **보행 실도로망 라우팅 엔진(OSRM, 이슈 #28)** 을 추가 컨테이너로 연동하여, 도보와 자전거 구간을 단순 직선이 아닌 골목길 실제 도로 형상으로 정밀하게 안내할 계획입니다."*
